# AI-Generated Code Review

Use this file when the code under review was written, or largely written, by an AI coding tool — a chat assistant, an IDE autocomplete, or an autonomous coding agent. Code written this way fails in a few recognizable, non-random ways, and a reviewer who only applies the generic checklist in `references/vulnerability-analysis.md` tends to miss them.

Treat this as an addition to that file, not a replacement for it. Everything in the vulnerability-analysis reference still applies here; this file covers what to look for on top of it.

## Why AI-Written Code Fails Differently

A model generates the version of a solution that's most statistically likely given the prompt and its training data, not the version that's been threat-modeled. Three patterns follow from that directly.

It solves the stated problem and nothing adjacent. Ask for "a function that uploads a file" and the model writes exactly that — upload logic — without validating file type, size, or content, because none of that was asked for and the happy path is what gets generated by default.

It reproduces whatever was common in its training data, security quality included. A huge share of public code on the internet has weak patterns baked in — string-concatenated SQL, disabled certificate verification in example snippets, `eval()` used for convenience. A model trained on that code reproduces the pattern, not because it's choosing to, but because that's what appeared most often for that kind of task.

It sounds confident regardless of whether the code is actually correct or safe. There's no hedging in generated code the way there sometimes is in a model's prose — a function that mishandles authentication reads exactly as clean and finished as one that doesn't.

## Vulnerability Patterns Specific to AI-Generated Code

### Package and Dependency Hallucination

A model asked to solve a problem in an unfamiliar or fast-moving ecosystem will sometimes invent a package name that sounds plausible but doesn't exist — `requests-auth-helper` instead of a real library, say. This is where slopsquatting comes in: an attacker registers that exact hallucinated name on a public package index ahead of time, banking on the fact that AI tools suggest the same hallucinated names often enough for someone to `pip install` or `npm install` it without checking. Any AI-suggested dependency needs a real existence and reputation check — download count, maintainer history, how long it's been published — before it goes into a project, not just a glance at whether the name looks right.

### Hardcoded Secrets in Example Code

Models frequently generate a working example with a placeholder API key, database password, or connection string inline, because that's the clearest way to demonstrate the pattern. The risk isn't the placeholder itself — it's that placeholders get copied straight into a real project and never swapped out for environment variables or a secrets manager before the code ships or gets committed.

### Security Controls Omitted by Default

Input validation, rate limiting, output encoding, authentication checks — these tend to show up only when explicitly asked for, because a prompt like "write an endpoint that returns user data" doesn't mention any of them and the model answers the question that was actually asked. The gap isn't usually a mistake in what got written; it's an absence of what wasn't.

### Outdated or Deprecated Patterns

Training data has a cutoff, and a model can suggest a library version, a crypto algorithm (MD5 for password hashing turns up more than it should), or an API call that was standard practice when the training data was collected and has since been deprecated or shown to be insecure. Checking "is this still the current recommended approach" matters more for AI-suggested code than for code a developer wrote by looking at current documentation.

### Overly Permissive Defaults

Faced with a choice between "this works for everyone" and "this works only for the people who should have access," a model optimizing for a working demo tends toward the former — a CORS policy with `*`, an IAM role scoped far wider than the task needs, a database query missing a `WHERE` clause that should scope results to the current user. None of this breaks the demo. All of it becomes a real vulnerability in production.

### Prompt Injection in LLM-Integrated Applications

If the code being reviewed itself calls an LLM — a chatbot, a summarizer, an agent with tool access — check whether untrusted input (user messages, scraped content, document text) gets concatenated into the model's prompt without separation from the system instructions, and whether the model's output then gets used to take an action (calling a tool, running a query, sending a request) without validation. An attacker who can influence the prompt can potentially hijack what the model does next. This is a newer vulnerability class with its own shape, closer in spirit to injection than to a classic logic bug, and worth treating as its own category rather than folding into generic input validation.

### Inconsistent Error Handling

Generated code sometimes wraps one function in a careful try/catch and leaves the next one completely bare, because each piece was generated somewhat independently even within a single file. The inconsistency itself is a tell that the code wasn't reviewed holistically — check whether error paths across the whole file leak stack traces, internal paths, or query details to the end user.

### Logic That Looks Right but Isn't

A model can misread context it wasn't given — an off-by-one in a loop boundary, a comparison operator that should be strict but isn't, an edge case (empty input, a negative number, a zero) that was never part of the training signal for this exact prompt. These aren't security bugs by category, but they often turn into them: an off-by-one in a permission check, for instance, is a logic bug with a security consequence.

## Review Checklist for AI-Generated Code

1. Verify every suggested dependency actually exists and has a credible maintenance history before it's added to the project.
2. Grep for anything that looks like a credential, token, or connection string, even ones that read as placeholders — confirm they're pulled from environment variables or a secrets manager before merging.
3. Check what the code does *not* handle: missing input validation, missing auth checks, missing rate limiting, on every new endpoint or entry point, since these are the parts least likely to have been asked for explicitly.
4. Confirm any cryptographic choice, library version, or API call against current guidance — don't assume what the model generated is still the current best practice.
5. Check every access-control boundary (CORS, IAM, query filters) for whether it's scoped to the minimum rather than left open for convenience.
6. For any code that builds a prompt for another LLM call, confirm untrusted input is isolated from system instructions and that model output isn't used to trigger an action without validation.
7. Read error handling across the whole file for consistency, not function by function in isolation.
8. Treat generated code with no obvious bug as unreviewed, not as safe — the absence of an obvious flaw is not the same as a security review having happened.

## When Explaining This to a User

Point out not just what's wrong in the code that exists, but what's conspicuously missing — the omissions are usually the bigger risk with AI-generated code, more than an outright mistake in the logic that's present. Frame feedback as "this works, and here's what it needs before anyone should trust it with real input," rather than treating a clean-looking function as finished.

## Worked Examples

**Input**: A developer pastes a Flask endpoint an AI assistant generated: it takes a `user_id` from the URL, queries a database for that user's profile, and returns it as JSON. No authentication check, no check that the requester is allowed to view that particular profile.

**Analysis**: The prompt that produced this almost certainly asked for "an endpoint that returns a user's profile by ID," and that's exactly what got built — nothing more. The missing authorization check is an omission, not a bug in what's there: there's no broken logic to point to, just a security control that was never part of the request. This is the pattern described above under "security controls omitted by default," and it's one of the most common findings in AI-generated endpoints specifically because access control is rarely implicit in how a task gets phrased.

**Output**: Finding: missing object-level authorization. A caller may be able to view another user's profile by changing the identifier, but confirm this with an authorized test account before claiming cross-account access. Fix: enforce authorization on the server for every requested object, using the authenticated identity and the application's access policy. Classification: CWE-639 if access is controlled by a user-supplied key. Do not add an ATT&CK technique unless observed adversary behavior supports one. Assess severity after confirming authentication requirements, data sensitivity, and reachable routes; do not assign a CVSS score from this example alone.

---

**Input**: An AI coding agent, asked to "add retry logic for failed API calls," imports a package called `fastapi-retry-utils` that the developer has never heard of and installs it without checking.

**Analysis**: This package name is plausible-sounding but worth treating as a hallucination risk until proven otherwise — "add retry logic" is exactly the kind of common, generic request where a model might reach for a package it's seen referenced somewhere in training data without confirming it actually exists under that name, or where it names something close to a real package. If the name is in fact hallucinated and someone has registered it on PyPI as a slopsquatting play, installing it hands that index entry direct code execution in the project.

**Output**: Before merging, verify the exact package name on the official package index, inspect its release history and maintainers, and compare it with established options such as `tenacity` for Python. If the package cannot be verified or its provenance is questionable, do not install it; select a known dependency or implement the small retry behavior using the standard library. A plausible or nonexistent name alone is not evidence of compromise. Consider supply-chain classifications only if a malicious or compromised package is actually identified; ATT&CK T1195 may be relevant when there is evidence of a supply-chain compromise.
